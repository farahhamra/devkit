# Optional Node measurement collector

Devkit's `performance` commands still analyze files offline. The separate, dependency-free Node helper in [integrations/node](../../integrations/node/) records measurements **inside an explicitly authorized ERP or Hub process**. It is not installed into either application automatically. Importing it starts no collectors, writes no files and opens no debug port. `startCollector()` is disabled unless `enabled: true` is passed. Node 20 and 24 are covered by the CI matrix.

The helper also ships in Python wheels at `devkit/node_collector/`. Locate an installed copy with:

```powershell
python -c "from importlib.resources import files; print(files('devkit').joinpath('node_collector'))"
```

There is no npm registry publication and no `devkit performance collect` command. An application-owned bootstrap/harness imports the helper from the checkout or installed directory. ESM can import directly; CommonJS uses dynamic `import()`. Keep application integration and collection runs separately authorized. The Devkit release is **not** evidence that an ElectroERP app adapter was installed or validated.

CommonJS needs a **native runtime** dynamic import. A TypeScript CommonJS compilation can rewrite `import()` to `require()`; inspect emitted output or use a small JavaScript `.cjs` loader that preserves native `import()`. Do not assume the source syntax alone establishes Node-version compatibility.

## Authorization and configuration

Before enabling collection, verify current entry points, actual Node/Prisma versions, middleware order, worker scope and startup side effects. Starting ElectroERP may seed data, start background jobs or contact external services; this helper does not authorize those actions or disable them. Do not start production or generate traffic implicitly.

This illustrative integration does not execute as part of Devkit:

```javascript
import { startCollector } from './path/to/devkit/integrations/node/collector.mjs';

// The application owns this explicit opt-in and chooses the authorized process/window.
const collector = await startCollector({
  enabled: approvedLocalCapture === true,
  workspaceRoot: electroErpRoot,       // existing absolute project root
  app: 'erp',                        // erp | hub; never both in one capture
  environment: 'local',              // local | staging only
  environmentId: 'developer-machine', // non-sensitive hardware/environment identity
  processScope: 'erp-worker-1',
  workload: 'sanitized-products-read',
  concurrency: 1,                    // actual declared workload; not generated by helper
  warmupMs: 0,                       // actual completed warmup; helper does not warm up
  durationMs: 60000,                 // requested cooperative stop; max 300000
  sampleIntervalMs: 1000,            // 10..60000; process-memory/cache sampling
  maxSamples: 2000,                  // 2..20000; bounded streams and event samples
  maxGroups: 500,                    // 1..2000 Prisma groups
  maxBytes: 12 * 1024 * 1024,        // 1024..16 MiB per output
  cpu: true,                        // separately opt in to CPU sampling; default false
});

// Observe status; unavailable/disabled/already_active is not a successful capture.
// The app runs its separately approved workload. The helper generates no traffic.
const result = await collector.stop(); // idempotent; early stop is allowed
```

`durationMs` is an event-loop timer, not hard preemption: a blocked main thread can delay stopping. CPU profiles are buffered by V8 until stop; node/sample/byte budgets are checked before publishing, not a guarantee against V8 allocation peaks. Other sample arrays and group counts are bounded during recording. Timers are unreferenced, so they cannot keep an otherwise exiting app alive. The caller owns graceful shutdown, e.g. awaiting `stop({ interrupted: true })` in its existing shutdown handler. No global signal handlers are installed and no app process is killed. A forced kill cannot produce a completed manifest. Only one session or heap operation can be active per process; duplicate starts do not attach another profiler.

Collector initialization/export errors return unavailable/limited status rather than changing app outcomes. Callers must check returned status and files. Scope labels and configuration must be non-sensitive. `environmentId`/`processScope` are declarations, not independently verified hardware identity.

GC event observation through `perf_hooks` does **not** need `--expose-gc`; that flag exposes forced GC, which this helper never invokes. `@types/node` and package dependency ranges do not establish actual versions: Node is recorded from `process.versions.node`, and the app must supply the resolved Prisma client version. Importing a factory such as `createApp()` can execute transitive module initialization; verify that graph before describing an in-process test as side-effect-free.

## Runtime and memory

Outputs include native V8 CPU samples when enabled, `monitorEventLoopDelay` distributions, event-loop utilization, observed `perf_hooks` GC entries and `process.memoryUsage()` samples. Nanoseconds are converted to milliseconds; percentiles come from the observed histogram, never averages. Empty histograms/unavailable instrumentation are explicit issues. GC events are observations, not proof of stop-the-world pauses. All process samples have `post_gc: false`; an asynchronous GC callback is insufficient to certify a post-GC sample.

Actual timestamps are preserved. CPU control-call bounds are labelled `control_bounds`, not falsely equated to the native profiler clock. Sample endpoints are not relabelled zero/duration to satisfy strict comparisons. **Completed collection does not mean complete analysis coverage**: omitted heaps, unknown post-GC boundaries and independently timed partial windows remain analyzer gaps. Existing comparison gates remain conservative, so ordinary runtime/memory/cache recordings may have metrics that cannot be compared. Collection windows document evidence; they do not override these gates.

CPU script URLs can contain local paths; raw snapshots/profiles are not guaranteed sanitized by output redaction. No original TypeScript source ranges are guessed from generated JavaScript.

## Prisma and request adapters

Pass optional `database` configuration with actual installed Prisma version, verified model fields and physical table mappings:

```javascript
database: {
  prismaVersion: actualPrismaVersion,
  engine: 'unknown', version: null, // no inference from documented minimum versions
  models: {
    Product: { fields: ['id', 'name'], tables: ['products'] }, // illustrative, verify live schema
  },
}
```

In an authorized Prisma version supporting `$use`, register `collector.prismaMiddleware` at the deliberately chosen boundary. Register `collector.expressMiddleware` before the request handlers to establish its own AsyncLocalStorage correlation. These are **manual integration steps**, not automatic patches. Middleware order matters: audit pre-reads, transactions and detached audit writes can produce overlapping logical operations. Verify the app's real behavior and supported Prisma API before installation. Newer clients without `$use` require an application adapter, not an assumed compatibility claim.

The adapter returns/rethrows the original operation results/errors. It groups logical Prisma operations by bounded, value-free shapes and explicit model/table mappings. Unknown fields are uninspected placeholders; oversized shapes and unsupported operations (including raw SQL) are dropped with explicit issues. It never retains arguments, query results or error strings. This is **not physical SQL timing**, SQL-plan export, lock/pool-wait measurement, or database index inventory. It does not query MySQL or alter Prisma logging.

Express `finish`/premature `close` count once, with request timing and local correlation IDs only. No URL, route parameters, headers, IPs or user data are captured. Route templates are omitted rather than guessed. Operations starting after a finished response are labelled detached when the context is retained; operations straddling completion have unknown phase rather than pretending all their time was detached. Missing context gives unknown phase, not presumed background work. Unfinished requests/operations at stop make collection incomplete; late completions cannot mutate written captures.

## Cache probes

```javascript
import { createCacheProbe } from './path/to/devkit/integrations/node/collector.mjs';
const probe = createCacheProbe({
  id: 'catalog-cache', backend: 'memory', scope: 'process',
  limits: { max_entries: 1000, max_bytes: null, ttl_ms: 30000 },
});
// Supply caches: [probe] to startCollector. The application explicitly records:
probe.lookup(wasActualHit, measuredLookupMs);
probe.size(measuredEntriesOrNull, measuredBytesOrNull);
// probe.reset() marks a true counter-lifetime reset with a new epoch.
```

No cache is created, monkey-patched or polled over the network. Record every observed lookup at the defined boundary. Unknown storage stays null; unmeasured secondary counters stay omitted. Latency includes measured count/total/min/max, not fabricated percentiles. Capacity/TTL values are declarations of actual policy: null means no bound, not unknown; omit `limits` if policy is unknown. No cache keys/values are accepted. A `Map` is not automatically a cache, and Redis-global counters must not be attributed to one logical cache.

With no configured probes, no `cache.json` is created and the session manifest says `not_configured`, not “no caches exist.” Browser TanStack Query and .NET Manager instrumentation are unsupported. Verify whether ElectroERP currently has backend caches before adding adapters.

## Local files and lifecycle contract

Each session uses a unique `diagnostics/performance/<uuid>/` inside the explicit workspace. A local `diagnostics/performance/.gitignore` containing `*` is created exclusively; conflicting existing content is rejected, not overwritten. This does not untrack previously committed files. Do not add this directory to Devkit's `.ignore` if you want offline analysis; explicit input paths cannot bypass that policy.

Files use restrictive POSIX permissions (0600 files/0700 newly created directories); on Windows verify inherited NTFS ACLs yourself. Symlinks/junctions and unsafe targets are refused. Complete capture files are published exclusively from temporary `.partial` files using hard links, so an existing destination is never replaced. Unsupported filesystems fail closed. Partial files can remain after export failure and may contain sensitive data; inspect status and manage them locally. No automatic upload or deletion/retention job occurs.

`session-start.json` records initiation. `session-complete.json` records successful publication and collection status; absent completion is not success. Analyze only completed JSON capture files, not session manifests or `.partial` files:

```powershell
devkit performance runtime --input diagnostics/performance/<uuid>/runtime.json --app erp --json
devkit performance memory --input diagnostics/performance/<uuid>/memory.json --app erp --json
devkit performance database --input diagnostics/performance/<uuid>/database.json --app erp --json
devkit performance cache --input diagnostics/performance/<uuid>/cache.json --app erp --json
```

Database input **1.1** and runtime/memory/cache input **2.1** retain their previous fields and require `collection`:

```json
{
  "status": "completed",
  "dropped_samples": 0,
  "issues": [],
  "windows": [
    {"stream": "process_samples", "start_ms": 0.5, "end_ms": 100.5, "boundary": "observed"}
  ]
}
```

The numbers above illustrate the shape, not measurements. Status is `completed`, `limited` or `interrupted`. Completed requires zero dropped observations and no issues. Issue codes are a fixed vocabulary: sample/size limits, collector/CPU/GC/event-loop/cache failures, unfinished/unsupported operations, unfinished requests, interruption, uncertain clock boundaries and heap-not-collected. Windows use actual monotonic millisecond offsets inside metadata duration; streams are unique and use `observed` or `control_bounds`. They are descriptive evidence, not alignment guarantees. Interrupted/limited captures cause coverage gaps, fail `--strict`, and cannot yield numeric comparisons. Old 1.0/2.0 inputs keep their old contract, including rejection of unknown fields.

## Separate heap capture

`captureHeap({ ...configuration, enabled: true, authorized: true, sanitizedData: true })` is a separate API, unavailable during an active collection. It exports a raw `.heapsnapshot`; native metadata/companion gaps still apply. It never forces GC. V8 may pause the process and allocate substantial memory before any bytes can be checked; output-byte limits are **not** a memory or pause-time guarantee. Use only separately approved sanitized local/staging processes. The analyzer's graph/value limits may still reject a snapshot under the byte limit; never trim a graph to make it pass.

## Validation and remaining app work

`node --test integrations/node/collector.test.mjs` checks lifecycle, limits, request/Prisma preservation, cache counters and file safety. Python interoperability tests execute a synthetic Node fixture and feed its actual captures to Devkit. These do not import ElectroERP, connect to databases or generate app traffic. The Windows/Node CI matrix is separate from locally executed tests.

Still required in ElectroERP: verify current bootstrap/Prisma/cache hooks; add authorized thin adapters; exercise representative sanitized workloads; measure disabled/enabled collector overhead; verify shutdown and multi-worker behavior; review capture privacy; and establish real comparable baselines. These tasks require the app checkout, investigation results and explicit runtime authorization.
